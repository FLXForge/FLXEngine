FLX Documentation

Roadmap

FLX is developed incrementally and through practical experimentation.

Each example adds new runtime capabilities, helps validate real architecture and reveals necessary improvements before moving forward.

This section acts as both a development diary and a general direction overview for the project.

Completed

Pong Example

First functional example used to build and validate the base engine structure.

Implemented systems

  • Base engine structure
  • Initial lifecycle
  • Movement API
  • Basic collisions
  • Horizontal and vertical bounce
  • Basic AI enemy
  • Respawn system (to_origin())
  • Log console
  • JSON and JavaScript support
  • JSON Schemas
  • TypeScript definitions (.d.ts)

In Development

Asteroids Example

Second runtime example.

Asteroids represents the first stage where FLX begins to define its internal model.

Beyond movement and shooting mechanics, this example is helping establish how objects are born, live, interact and disappear inside the runtime.

Currently used to validate:

  • Shape system (shape).
  • JSON-based motion system.
  • Rotation and unified FLX angular convention, also applied to Pong.
  • New API functions and runtime scripting evolution.
  • Screen wrapping and bounds behavior.
  • Living HTML documentation synchronized with real development.
  • Real color support from JSON.
  • New shape.type = line shape.
  • Scalable input system: Key.down(KEY_*) and Key.pressed(KEY_*).
  • KEY_* constants exposed to JavaScript.
  • Probability system: probability(chance, base).
  • Declarative spawns defined directly in JSON.
  • Prefabs loaded and cached without immediate instantiation.
  • Runtime instantiation through spawn(self, "laser").
  • Dynamic object creation from prefabs.
  • Safe spawn queue through pendingObjects and flushSpawnQueue().
  • Decoupled world entry: spawn(), queue, born() and runtime integration.
  • Local offsets rotated according to object angle.
  • Prefab script loading and caching through ScriptEngine.
  • Fully functional ship firing system.
  • Complete lifecycle: start(), born(), action(), motion(), collision(), kill(), dead() and cleanup().
  • Deferred destruction through kill(object).
  • alive state used to exclude dead objects from runtime phases.
  • dead() phase executed only once before cleanup.
  • Per-instance initialization through born().
  • Persistent per-object state through object.local.
  • Real frame timing through delta().
  • Scope model: function scope, script scope, object.local and future global scope.

Currently in Development

  • Complex object spawning, especially asteroids.
  • UI and text systems.
  • game / level context.
  • Signals and object-to-object communication.
  • Runtime object relationships: parent, children and group access.
  • Configurable death propagation between related objects.
  • Extending object.local beyond numeric values.

Next Phase

After completing the three main examples, FLX will enter a normalization and refinement phase.

The objective will be:

  • Unify architecture and naming
  • Refine APIs
  • Reduce duplication
  • Improve runtime consistency
  • Make the examples more complete and polished

Technical Debt and Pending Improvements

  • Normalize Pong to the new shape/motion schema.
  • Review whether program remains the final name.
  • Centralize JavaScript wrapper functions to avoid modifying multiple locations whenever a new lifecycle is introduced.
  • Refactor the JS wrapper using a centralized function registry.
  • Normalize JSON paths in the same way as script paths.
  • Improve warnings: optional lifecycle functions should not generate warnings when absent.
  • Extend object.local. It currently supports only numeric values; types such as bool, string and possibly more complex structures remain pending.
  • Define a persistent global scope, suitable for scores, shared state and runtime-wide data.
  • Define game/level context and persistence between levels.
  • Define runtime object relationships: parent, children and access through group.
  • Define configurable death propagation, for example deciding whether kill(parent) should also affect its children.
  • Properly implement motion.inherit = live.
  • Explore a semantic input layer (Control.*) on top of Key.
  • Properly separate and document block, rectangle and triangle.
  • Improve overflow-aware collisions.
  • Future: wrap-aware collisions using radii and positional offsets.
