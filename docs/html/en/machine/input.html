Input Chip defines which logical controls exist. It declares their budgets and resolution rules. The physical input that activates each control is assigned in another file, Input Mapping.

Controls and defaults

Independent budgets
FieldType / valuesDefaultBehavior in v0.3.0
system.buttonsInteger ≥ 02Global logical buttons, independent of players. The chip does not assign meanings such as Start or Select to them.
players.countInteger ≥ 11Number of available logical players.
players.controls.buttonsInteger ≥ 04Number of logical buttons per player.
players.controls.directionsNonempty array of mapsOne 4way directionList of independent directional controls available to each player. A declared array replaces the default list.

Players are identified starting at 1; buttons and directions starting at 0. For example, two directions per player are direction 0 and direction 1. Omitting directions preserves the default direction; declaring it empty produces an error diagnostic.

Default Input Chip
machine:
  input:
    system:
      buttons: 2
    players:
      count: 1
      controls:
        buttons: 4
        directions:
          - type: 4way
            simultaneous: last
            buffer: 0

4way

Sign convention by axis
        UP (−1)
           │
LEFT (−1) ─┼─ RIGHT (+1)
           │
       DOWN (+1)

A 4way control has a single active logical component, or neutral. It does not produce diagonals: simultaneous decides which component prevails. The axis query convention is UP = −1 and DOWN = +1 vertically; LEFT = −1 and RIGHT = +1 horizontally. These are signs of directional state, not a declaration of additional JavaScript constants.

2way

Logical state
NEGATIVE (−1) ← neutral (0) → POSITIVE (+1)

The public mapping can use the names up, right, down and left. For a 2way control, they are normalized as follows:

Mapping name normalization
Public nameLogical component
up, leftnegative (−1)
down, rightpositive (+1)

This grouping identifies alternatives for the same component; it does not require both names to be activated at once. The simultaneous policy operates on normalized components.

Simultaneous

Simultaneity resolution
ValueBehavior
lastThe most recently activated component among those still active wins.
firstThe dominant component retains control while it remains active. When it disappears, a valid pending candidate can be promoted; if there is none, resolution is performed again among the components still active.
neutralMore than one active component produces neutral; a single active component is retained.

Each direction resolves its own simultaneity. Having multiple directions per player does not turn them into a single combined control.

Buffer

Buffer is not a generic input queue. In simultaneous: first, it lets a blocked candidate component be retained temporarily while another remains dominant. That candidate can take control when the dominant component disappears, provided the candidate remains active. Time is expressed in seconds.

It does not guarantee later execution of a press already released: a candidate that stops being active is discarded. With last or neutral, buffer does not modify resolution. The default 0 does not retain a candidate through this mechanism.

Two directional controls per player
machine:
  input:
    players:
      count: 1
      controls:
        buttons: 2
        directions:
          - type: 4way
            simultaneous: first
            buffer: 0.15
          - type: 2way
            simultaneous: neutral
            buffer: 0

Valid mapping snippet
players.1.directions.0.up=KEY_W
players.1.directions.0.right=KEY_D
players.1.directions.0.down=KEY_S
players.1.directions.0.left=KEY_A

These physical inputs belong to the mapping, not the Machine Input definition. The project selects the file through input.mapping in Project. Changing physical bindings should not require changing the JSON world or scripts that query the same logical controls.

Read calls are documented in FLX API. Associating an object with a player belongs to Object.control.

Unsupported capabilities

input.pointer and input.text are not available capabilities in v0.3.0. Declaring them produces an unsupported Machine diagnostic. Likewise, directional types other than 2way and 4way are not accepted as implemented. These are not future fields that silently work.
