Diagnostics

Diagnostic fields · Severities · Domains and codes · Location · Text output · JSON output · Diagnostics and exit codes

A diagnostic represents structured information produced by an FLX subsystem. It lets you communicate an issue to a person and classify it in a tool without relying on the message text.

Public model
Diagnostic
├── severity
├── code
├── identifier
├── file
├── field
├── message
└── range?

Diagnostic fields

Public JSON form
FieldTypeMeaning
severityStringinfo, warning or error.
codeStringStable machine-readable code, such as FLX-RESOURCE-00010.
identifierStringStable symbolic identifier for the code, such as MissingReferencedResource.
fileStringContext file; an empty string if not provided.
fieldStringContext field; an empty string if not provided.
messageStringSpecific explanation of this occurrence of the diagnostic.
rangeOptional objectSource position, only when available.
Identity and detail
code       = FLX-RESOURCE-00010
identifier = MissingReferencedResource
message    = specific details of the missing resource

For external integrations, use code as the stable identifier of the diagnostic type. identifier provides its symbolic name, and message describes the specific occurrence. The message may change to improve the explanation without changing the diagnostic's identity.

Severities

Interpreting severity
SeverityMeaning
infoInformation about the operation.
warningWarning that does not, by itself, imply the operation failed.
errorError issue. hasErrors() returns true if at least one diagnostic has this severity.

Severity belongs to each occurrence of a diagnostic. The registry contains a typical severity per code; use the result's field to interpret it: severity.

Domains and codes

Codes follow FLX-DOMAIN-NNNNN: FLX prefix, domain and five digits. The registered domains are:

Diagnostic areas
DomainArea
CLICommands and arguments.
PROJECTManifest and project resolution.
COMPCompilation and compiled project consistency.
RESOURCEResources and references.
MACHINEConfiguration of Machine and its chips.
INPUTInput mapping and controls.
BINARYReading, writing and format of the compiled project.
RUNTIMELoading and execution with Engine.
BUILDRegistered build domain; does not imply an available build command.

Each domain reserves the suffixes 00000 (information), 00001 (warning), 00002 (error), 00003 (internal error) and 00004 (deprecated functionality). There are also specific codes; this selection is not an exhaustive catalog.

Examples from the current registry
CodeIdentifierMeaning
FLX-CLI-00002CliErrorUnclassifiedGeneric CLI error.
FLX-PROJECT-00010ProjectManifestCouldNotBeOpenedCould not open the manifest.
FLX-RESOURCE-00010MissingReferencedResourceA referenced resource was not found.

FLX-RUNTIME-00015RuntimeLoadSpawnLimitExceededThe spawn limit was exceeded while loading the runtime.

Location

file and field add context when available. Not every diagnostic identifies a file, field or range. In JSON, file and field are always present as strings; range is omitted when unavailable.

Snippet of a diagnostic with a range
"range": {
  "startLine": 2,
  "startColumn": 4,
  "endLine": 2,
  "endColumn": 11
}

The four values are integers identifying the start and end lines and columns supplied by the producer. The model itself establishes no universal inclusive/exclusive endpoint convention and does not guarantee a range for every issue.

Text output

Format example, verified by tests
error FLX-CLI-00002 CliErrorUnclassified: game/root.json [children.ship]: Invalid child

The format starts with severity, code and identifier, followed by a colon. If a file is present, it is added along with the field in brackets, if available; the message follows. The current text printer does not show the range and only shows the field when a file is also present.

All text diagnostics are written to stderr, including info and warning. The normal success message from compile or validate goes to stdout. This lets you separate the result from the issues.

JSON output

With --format=json recognized by the CLI, compile and validate write the full structured result to stdout; the diagnostic printer leaves stderr empty. This format is not offered for runtime commands. See CLI · Output format.

Conceptual envelope
{
  "success": false,
  "command": "compile",
  "exitCode": 4,
  "diagnostics": []
}

The array contains the operation's diagnostics; the example above only shows the structure. A successful result also includes message with the overall result message. That field is distinct from the message inside each diagnostic.

Conceptual example of a diagnostics element
{
  "severity": "error",
  "code": "FLX-RESOURCE-00010",
  "identifier": "MissingReferencedResource",
  "file": "objects/player.json",
  "field": "children.laser",
  "message": "Referenced resource was not found."
}

Each element contains the six string fields shown; it only adds range when available. Do not depend on JSON object key order.

The parser processes arguments in order and stops on an error. Therefore, flx validate --unknown --format=json . still fails in text mode, whereas flx validate --format=json --unknown . emits a JSON result. Having the option at the end of an invalid invocation does not guarantee the format.

Diagnostics and exit codes

Two levels of information
exit code
└── overall category of the command result

diagnostics
└── specific information about what happened

A command can complete successfully and produce warnings. Check success and exitCode for the overall result, and iterate through diagnostics for details. The table of CLI exit codes distinguishes defined codes from the current functional paths.
