A Machine defines the capabilities and constraints of the environment in which an FLX project runs. Describes the project's execution possibilities; entities and behavior are declared in other layers.

Separation of responsibilities
Objects declare what exists.
Scripts declare what it does.
Machine declares what the world can do.

Three chips

Machine
Machine
├── Video
├── Audio
└── Input
  • Video — logical screen, color capabilities and physical presentation.
  • Audio — available voices, synthesis and audio fidelity.
  • Input — players, logical buttons and directional controls.

Machine does not describe the game: it contains no objects, songs, actions such as “fire” or behaviors. It establishes the capabilities those declarations work with.

Selection from the project

.flx manifest entry
machine=machines/asteroidsMachine.yml

The path is resolved relative to the .flx manifest directory, not its JSON content path. If the project does not select its own Machine, it uses the internal Default Machine. See Project.

Canonical structure

Partial Machine with all three chips
machine:
  video:
    screen:
      width: 320
      height: 240
  audio:
    voices:
      music: 3
      sound: 1
  input:
    players:
      count: 1

The canonical form uses the root machine:. The loader also accepts the blocks video, audio and input directly at the file root as an alternative format. The public properties in this reference are the capabilities of those three chips.

Inline and external chips

Each chip can be an inline YAML map or a string containing an external file path. Chip paths are resolved relative to the Machine file declaring them; include the resource extension.

Machine with inline Video
machine:
  video:
    screen:
      width: 320
      height: 240
Machine with external Video
machine:
  video: chips/video/retro.yml
chips/video/retro.yml — relative to the Machine file
video:
  screen:
    width: 320
    height: 240

The external file must contain a map with the corresponding chip root: video:, audio: or input:. You can mix inline and external chips in one Machine.

Partial Machine and defaults

Loading starts from an internal default definition and overlays declared fields. Omitting a chip preserves its default capabilities: not declaring audio does not disable audio. When players.controls.directions is declared, the specified list replaces the default direction. Specific rules for other blocks, such as color.palette, are detailed in each chip's reference.

Main defaults
ChipInitial definition
Video640 × 480; clear color black; output.scale: 1; output.smoothing: false.
Audio8 music voices and 16 sound voices; mode shared; overflow replace_oldest; model open.
Input2 system buttons; 1 player; 4 buttons per player; one 4way direction, with simultaneous: last and buffer: 0.

Complete defaults and ranges are detailed in each chip. A zero value has its own meaning where supported; it is not equivalent to omitting the field.

Accepted format and effective capability

A property being accepted and stored does not imply it already has applied or distinct behavior. This reference distinguishes effective capabilities, values sharing an implementation, and properties with no functional effect yet. Details for each case are in Video, Audio and Input.

The examples show valid values and use true/false for booleans. The loader issues warnings and falls back to defaults for several invalid fields; unsupported Input capabilities generate an error diagnostic. Do not infer support for a property merely because a file can be loaded.
