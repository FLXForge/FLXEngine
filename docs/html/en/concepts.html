FLX Documentation

Basic concepts

FLX organizes projects through simple data structures, objects, behavior and clearly defined execution rules.

This section describes the fundamental concepts that are part of any FLX project.

Project

Every FLX project starts with a project file with the extension .flx.

This file acts as the project's entry point.

asteroids.flx
title=Asteroids
name=Asteroids
version=2.0
engine=0.3.0

path=asteroids
root=space
machine=machines/asteroidsMachine.yml
input.mapping=controllers.input

From this file, the runtime loads the root object, resources and project configuration.

Machine

Every project runs on a machine, which defines the characteristics of the environment in which the world operates.

A project can select its machine through the machine field in the .flx file. If not declared, FLX uses the default configuration.

Machines are described in detail in their own documentation section.

Root object

The root object is the object selected by the root field in the .flx file.

It is a regular JSON object that organizes the world's main structure and associated resources.

Depending on the project, it may represent:

  • A level
  • A menu
  • A loading screen
  • A presentation
  • A narrative sequence
  • A particular application state

FLX does not impose a particular interpretation.

Objects

Objects represent elements that exist within the runtime.

An object can:

  • Be drawn
  • Move
  • Collide
  • Store data
  • Execute behavior through scripts

Objects are usually described using JSON.

A definition can be written in full or built by reusing another definition through like.

ship.json
{
    "size": {
        "width": 18,
        "height": 24
    },

    "visual": {
        "representation": [
            {
                "primitive": "triangle",
                "mode": "outline"
            }
        ]
    },

    "mechanics": {
        "type": "polar",
        "motion": {
            "speed": { "limit": 180 }
        }
    }
}

Reuse and composition

FLX lets you build new definitions from existing ones.

This capability is based on the like system, which lets you reuse configurations and override only the fields you need.

DeepSpaceLeft
{
    "like": "asteroid/deep_space",

    "origin": {
        "x": 5,
        "y": 5
    }
}

This feature lets you build entire object families by reusing a single base definition.

An object does not need a visual representation to exist within the runtime.

If it defines behavior, children or collisions, it can act as a logical node, level manager, HUD, spawner, trigger or game controller.

During execution, name retains the object definition's logical name, while id identifies a specific instance within the runtime.

Full details are described in JSON Reference.

Children and spawn timing

children declares which objects a parent object can create. Each child's spawn value determines whether its first instance is born automatically or remains available for manual creation.

creation defines how the parent organizes the creation of its children. If not declared, the mode used is individual.

  • spawn: "auto": the child is instantiated when its parent enters the world.
  • spawn: "manual": the child is registered and can be created later with spawn(parent, "child").

spawn(parent, "child") can create any declared child. The spawn value only controls whether the first instance is born automatically when the parent enters the world.

Visual representation

An object's appearance is declared through visual.

An object can contain multiple elements within representation. Each element can be a primitive, geometry defined by points or text.

Representation Usage
primitive Basic shapes: rectangle, triangle and ellipse.
geometry Geometry defined by a list of points.
text Text with configurable font size.

visual can define a base color, and each element of representation can use its own color.

visual
"visual": {
    "color": "white",
    "representation": [
        {
            "primitive": "triangle",
            "mode": "outline"
        }
    ]
}

Geometries let you build representations from points and choose whether they are drawn open, closed or filled.

geometry
"visual": {
    "representation": [
        {
            "geometry": [
                { "x": 0, "y": -16 },
                { "x": 12, "y": 8 },
                { "x": -12, "y": 8 }
            ],
            "mode": "close"
        }
    ]
}

Visual representation and collisions

In FLX, visual representation and collision are independent systems.

The visual block defines how an object is represented, while collisions defines its colliders and how they participate in collision detection.

In some cases, both definitions may be similar, but they do not have to match.

Each collider can be enabled or disabled and declare through with the groups against which it queries collisions.

Collision checks are directional: an object only executes collision(object, other, contacts) when one of its enabled colliders includes the other object's group in its with list.

visual + collisions
{
    "visual": {
        "representation": [
            {
                "primitive": "triangle",
                "mode": "outline"
            }
        ]
    },

    "collisions": {
        "body": {
            "type": "ellipse",
            "size": {
                "width": 24,
                "height": 24
            }
        }
    }
}

This separation lets you define representation and collision detection independently.

Coordinate system

FLX uses a 2D coordinate system. In the current machine, the logical origin is at the top-left corner.

  • x increases to the right.
  • y increases downward.
  • Moving up means decreasing y.
  • Moving down means increasing y.

FLX currently works with logical world coordinates in a fixed world without a camera or scrolling.

Objects use these coordinates for their position within the runtime. Immediate drawing functions, such as draw_text(), use logical world coordinates by default, or local coordinates when a RuntimeObject is passed as a reference.

Angle system

FLX uses its own angular convention.

  • 0° points up.
  • 90° points right.
  • 180° points down.
  • 270° points left.
  • Positive angles rotate clockwise.
rotation
rotate(ship, 1);   // gira en sentido horario
rotate(ship, -1);  // gira en sentido antihorario

In polar movement, advance() uses the object's current angle to determine the direction of travel.

Movement

An object's movement is configured through mechanics.

FLX distinguishes two main models:

  • direct: movement along the horizontal and vertical axes.
  • polar: movement defined by speed and angle.

mechanics can declare speed, acceleration, inertia and other movement and rotation characteristics.

During execution, the runtime maintains live movement state. Scripts can query values such as speed, angle, velocityX, velocityY and rotationSpeed through the object received by hooks.

Movement operations, such as move_horizontal(), move_vertical(), advance(), accelerate() or rotate(), act on that state while respecting the declared mechanics.
