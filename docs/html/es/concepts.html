Documentación FLX

Conceptos básicos

FLX organiza los proyectos mediante estructuras de datos simples, objetos, comportamiento y reglas de ejecución claramente definidas.

Esta sección describe los conceptos fundamentales que forman parte de cualquier proyecto FLX.

Proyecto

Todo proyecto FLX comienza con un archivo de proyecto con extensión .flx.

Este archivo actúa como punto de entrada del proyecto.

asteroids.flx
title=Asteroids
name=Asteroids
version=2.0
engine=0.3.0

path=asteroids
root=space
machine=machines/asteroidsMachine.yml
input.mapping=controllers.input

A partir de este archivo, el runtime carga el objeto raíz, los recursos y la configuración del proyecto.

Objeto raíz

El objeto raíz es el objeto seleccionado por el campo root del archivo .flx.

Es un objeto JSON normal que organiza la estructura principal del mundo y los recursos asociados.

Dependiendo del proyecto, puede representar:

  • Un nivel
  • Un menú
  • Una pantalla de carga
  • Una presentación
  • Una secuencia narrativa
  • Un estado concreto de la aplicación

FLX no impone una interpretación concreta.

Objetos

Los objetos representan elementos que existen dentro del runtime.

Un objeto puede:

  • Dibujarse
  • Moverse
  • Colisionar
  • Almacenar datos
  • Ejecutar comportamiento mediante scripts

Normalmente los objetos se describen mediante JSON.

Una definición puede escribirse completamente o construirse reutilizando otra definición mediante like.

ship.json
{
    "size": {
        "width": 18,
        "height": 24
    },

    "visual": {
        "representation": [
            {
                "primitive": "triangle",
                "mode": "outline"
            }
        ]
    },

    "mechanics": {
        "type": "polar",
        "motion": {
            "speed": { "limit": 180 }
        }
    }
}

Reutilización y composición

FLX permite construir nuevas definiciones a partir de otras ya existentes.

Esta capacidad se basa en el sistema like, que permite reutilizar configuraciones y sobrescribir únicamente los campos necesarios.

DeepSpaceLeft
{
    "like": "asteroid/deep_space",

    "origin": {
        "x": 5,
        "y": 5
    }
}

Esta característica permite construir familias completas de objetos reutilizando una única definición base.

Un objeto no necesita tener representación visual para existir dentro del runtime.

Si define behavior, children o collisions, puede actuar como nodo lógico, gestor de nivel, HUD, spawner, trigger o controlador de juego.

Durante la ejecución, name conserva el nombre lógico de la definición del objeto, mientras que id identifica una instancia concreta dentro del runtime.

Los detalles completos se describen en JSON Reference.

Children y momento de spawn

children declara qué objetos puede crear un objeto padre. El valor spawn de cada hijo determina si su primera instancia nace automáticamente o queda disponible para creación manual.

creation define cómo organiza el padre la creación de sus hijos. Si no se declara, el modo utilizado es individual.

  • spawn: "auto": el hijo se instancia cuando su padre entra en el mundo.
  • spawn: "manual": el hijo queda registrado y puede crearse después con spawn(parent, "child").

spawn(parent, "child") puede crear cualquier hijo declarado. El valor spawn solo controla si la primera instancia nace automáticamente cuando el padre entra en el mundo.

Representación visual

La apariencia de un objeto se declara mediante visual.

Un objeto puede contener varios elementos dentro de representation. Cada elemento puede ser una primitiva, una geometría definida mediante puntos o un texto.

Representación Uso
primitive Formas básicas: rectangle, triangle y ellipse.
geometry Geometría definida mediante una lista de puntos.
text Texto con tamaño de fuente configurable.

visual puede definir un color base y cada elemento de representation puede utilizar su propio color.

visual
"visual": {
    "color": "white",
    "representation": [
        {
            "primitive": "triangle",
            "mode": "outline"
        }
    ]
}

Las geometrías permiten construir representaciones mediante puntos y elegir si se dibujan abiertas, cerradas o rellenas.

geometry
"visual": {
    "representation": [
        {
            "geometry": [
                { "x": 0, "y": -16 },
                { "x": 12, "y": 8 },
                { "x": -12, "y": 8 }
            ],
            "mode": "close"
        }
    ]
}

Representación visual y colisiones

En FLX, la representación visual y la colisión son sistemas independientes.

El bloque visual define cómo se representa un objeto, mientras que collisions define sus colliders y cómo participan en la detección de colisiones.

En algunos casos ambas definiciones pueden ser similares, pero no tienen por qué coincidir.

Cada collider puede estar habilitado o deshabilitado y declarar mediante with los grupos con los que consulta colisión.

Las comprobaciones de colisión son direccionales: un objeto solo ejecuta collision(object, other, contacts) cuando uno de sus colliders habilitados incluye el grupo del otro objeto en su lista with.

visual + collisions
{
    "visual": {
        "representation": [
            {
                "primitive": "triangle",
                "mode": "outline"
            }
        ]
    },

    "collisions": {
        "body": {
            "type": "ellipse",
            "size": {
                "width": 24,
                "height": 24
            }
        }
    }
}

Esta separación permite definir la representación y la detección de colisiones de forma independiente.

Sistema de coordenadas

FLX utiliza un sistema de coordenadas 2D. En la máquina actual, el origen lógico se encuentra en la esquina superior izquierda.

  • x crece hacia la derecha.
  • y crece hacia abajo.
  • Subir implica reducir y.
  • Bajar implica aumentar y.

Actualmente FLX trabaja con coordenadas lógicas de mundo en un mundo fijo sin cámara ni scroll.

Los objetos utilizan estas coordenadas para su posición dentro del runtime. Las funciones de dibujo inmediato, como draw_text(), usan coordenadas lógicas de mundo por defecto, o coordenadas locales cuando se pasa un RuntimeObject como referencia.

Sistema angular

FLX utiliza una convención angular propia.

  • 0° apunta hacia arriba.
  • 90° apunta hacia la derecha.
  • 180° apunta hacia abajo.
  • 270° apunta hacia la izquierda.
  • Los ángulos positivos giran en sentido horario.
rotation
rotate(ship, 1);   // gira en sentido horario
rotate(ship, -1);  // gira en sentido antihorario

En movimiento polar, advance() utiliza el ángulo actual del objeto para determinar la dirección de avance.

Movimiento

El movimiento de un objeto se configura mediante mechanics.

FLX distingue dos modelos principales:

  • direct: movimiento sobre los ejes horizontal y vertical.
  • polar: movimiento definido mediante velocidad y ángulo.

mechanics puede declarar velocidad, aceleración, inercia y otras características del movimiento y la rotación.

Durante la ejecución, el runtime mantiene el estado vivo del movimiento. Los scripts pueden consultar valores como speed, angle, velocityX, velocityY y rotationSpeed a través del objeto recibido por los hooks.

Las operaciones de movimiento, como move_horizontal(), move_vertical(), advance(), accelerate() o rotate(), actúan sobre ese estado respetando las mechanics declaradas.
