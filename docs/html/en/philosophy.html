FLX Documentation

Philosophy

FLX comes from a simple idea: get results without fighting the tools.

Too often, simple ideas end up buried under complex configurations, hard-to-understand architectures or workflows that require learning the tool before developing the project.

FLX tries to reduce that friction.

Why FLX exists

FLX is designed for people who want to build something quickly, understand how it works and retain control over what they are creating.

Whether it is a prototype, a game jam, a complete game or an interactive tool, the intention is the same:

Build without fighting the engine.

Simplicity through understanding

FLX does not try to hide the rules it operates by.

It tries to keep those rules few, clear and predictable.

The idea is to use simple, predictable structures so that behavior can be easily understood, modified and extended.

Simplicity does not come from hiding complexity.

It comes from organizing it clearly.

Data, functions and runtime

FLX is built around three fundamental concepts:

Mental model
Objects -> Data

Scripts -> Functions

Runtime -> Connects both

Objects describe what exists.

Scripts describe what happens.

The runtime coordinates the interaction between both.

This model lets you build complex behavior using relatively simple structures.

Based on standards

FLX avoids unnecessary proprietary systems.

Projects use widely known technologies:

  • JSON for structured data
  • JavaScript for scripting
  • Standard resource formats
  • Readable, editable text files

The goal is for developers to use tools they already know.

Declaration and behavior

FLX makes it easy to declare many common behaviors and capabilities.

When an object needs specific behavior, scripts can work with its state and use the operations provided by the runtime.

The declaration establishes the object's capabilities; the script expresses how to use them during execution.

Small, clear and direct

FLX is particularly suited to:

  • Prototypes
  • Game jams
  • Arcade games
  • Small and medium-sized 2D projects
  • Experimental ideas

It does not try to be the solution to every problem.

It tries to be a clear tool for solving some of them well.

What FLX does not aim to be

FLX does not try to compete with large-scale general-purpose engines.

It does not try to hide how the runtime works behind increasingly complex layers of abstraction.

And it does not try to replace technical knowledge with automation.

FLX aims to help developers understand what happens, why it happens and how to change it.
