Diagnostics

Campos del diagnóstico · Severidades · Dominios y códigos · Localización · Salida textual · Salida JSON · Diagnostics y códigos de salida

Un diagnostic representa información estructurada producida por un subsistema FLX. Permite comunicar una incidencia a una persona y clasificarla desde una herramienta sin depender del texto de su mensaje.

Modelo público
Diagnostic
├── severity
├── code
├── identifier
├── file
├── field
├── message
└── range?

Campos del diagnóstico

Forma pública en JSON
CampoTipoSignificado
severityCadenainfo, warning o error.
codeCadenaCódigo estable legible por herramientas, como FLX-RESOURCE-00010.
identifierCadenaIdentificador simbólico estable del código, como MissingReferencedResource.
fileCadenaArchivo de contexto; cadena vacía si no se proporciona.
fieldCadenaCampo de contexto; cadena vacía si no se proporciona.
messageCadenaExplicación concreta de esta aparición del diagnóstico.
rangeObjeto opcionalPosición de origen, sólo cuando existe.
Identidad y detalle
code       = FLX-RESOURCE-00010
identifier = MissingReferencedResource
message    = detalle concreto del recurso que falta

Para integraciones externas, utiliza code como identificador estable del tipo de diagnóstico. identifier proporciona su nombre simbólico y message describe la aparición concreta. El mensaje puede cambiar para mejorar la explicación sin cambiar la identidad del diagnóstico.

Severidades

Interpretación de severity
SeveridadSignificado
infoInformación sobre la operación.
warningAdvertencia que no implica por sí sola que la operación haya fallado.
errorIncidencia de error. hasErrors() devuelve true si existe al menos un diagnóstico con esta severidad.

La severidad pertenece a cada aparición del diagnóstico. El registro contiene una severidad habitual por código; para interpretar un resultado utiliza su campo severity.

Dominios y códigos

Los códigos siguen FLX-DOMAIN-NNNNN: prefijo FLX, dominio y cinco dígitos. Los dominios registrados son:

Áreas de diagnóstico
DominioÁrea
CLIComandos y argumentos.
PROJECTManifiesto y resolución del proyecto.
COMPCompilación y consistencia del proyecto compilado.
RESOURCERecursos y referencias.
MACHINEConfiguración de Machine y sus chips.
INPUTMapping y controles de entrada.
BINARYLectura, escritura y formato del proyecto compilado.
RUNTIMECarga y ejecución con Engine.
BUILDDominio registrado para construcción; no implica un comando build disponible.

Cada dominio reserva los sufijos 00000 (información), 00001 (warning), 00002 (error), 00003 (error interno) y 00004 (funcionalidad obsoleta). Hay además códigos específicos; esta selección no es un catálogo exhaustivo.

Localización

file y field añaden contexto cuando está disponible. No todos los diagnósticos identifican un fichero, campo o rango. En JSON, file y field siempre están presentes como cadenas; range se omite cuando no existe.

Fragmento de un diagnóstico con rango
"range": {
  "startLine": 2,
  "startColumn": 4,
  "endLine": 2,
  "endColumn": 11
}

Los cuatro valores son enteros que identifican las líneas y columnas de inicio y fin proporcionadas por el productor. El modelo por sí solo no establece una convención universal de extremo inclusivo/exclusivo ni garantiza rango para todas las incidencias.

Salida textual

Ejemplo de formato, verificado por los tests
error FLX-CLI-00002 CliErrorUnclassified: game/root.json [children.ship]: Invalid child

El formato comienza con severidad, código e identifier, seguidos de dos puntos. Si hay archivo, se añade éste y, si existe, el campo entre corchetes; después aparece el mensaje. El impresor textual actual no muestra el rango y sólo muestra el campo cuando también hay archivo.

Todos los diagnósticos textuales se escriben en stderr, incluidos info y warning. El mensaje normal de resultado satisfactorio de compile o validate va a stdout. Así pueden separarse el resultado y las incidencias.

Salida JSON

Con --format=json reconocido por el CLI, compile y validate escriben el resultado estructurado completo en stdout; el impresor de diagnósticos deja stderr vacío. No se ofrece este formato para los comandos de runtime. Consulta CLI · Formato de salida.

Envelope conceptual
{
  "success": false,
  "command": "compile",
  "exitCode": 4,
  "diagnostics": []
}

El array contiene los diagnósticos de la operación; el ejemplo anterior sólo muestra la estructura. Un resultado satisfactorio incluye además message con el mensaje global del resultado. Ese campo es distinto del message dentro de cada diagnóstico.

Ejemplo conceptual de un elemento de diagnostics
{
  "severity": "error",
  "code": "FLX-RESOURCE-00010",
  "identifier": "MissingReferencedResource",
  "file": "objects/player.json",
  "field": "children.laser",
  "message": "Referenced resource was not found."
}

Cada elemento contiene los seis campos de cadena mostrados; sólo añade range cuando existe. No dependas del orden de las claves del objeto JSON.

El parser procesa los argumentos en orden y se detiene ante un error. Por ello, flx validate --unknown --format=json . falla todavía en texto, mientras que flx validate --format=json --unknown . emite un resultado JSON. La presencia de la opción al final de una invocación inválida no garantiza el formato.

Diagnostics y códigos de salida

Dos niveles de información
exit code
└── categoría global del resultado del comando

diagnostics
└── información concreta sobre lo ocurrido

Un comando puede terminar correctamente y producir warnings. Comprueba success y exitCode para el resultado global, y recorre diagnostics para los detalles. La tabla de códigos de salida del CLI distingue los códigos definidos de los caminos funcionales actuales.
