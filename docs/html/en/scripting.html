FLX Documentation

Scripting

Scripts define object behavior during execution.

However, to understand scripting in FLX correctly, it is important to set aside some common ideas found in other engines.

The idea behind scripting in FLX

Many engines organize behavior through classes, components or systems where each object has its own methods.

FLX takes a different approach.

Mental model
Object  -> Data

Script  -> Functions

Runtime -> Connects both

Objects contain state.

Scripts contain functions.

The runtime executes functions and provides them with the objects they should act on.

FLX does not try to turn JavaScript into C++.

It aims to let runtime behavior be written as scripts.

Scripting model

An FLX script is not a class.

Nor is it a separate instance for each object.

It is a shared JavaScript module.

The runtime loads the script once and reuses its functions for every object that needs them.

ship.js
function action(ship) {
    accelerate(ship);
}

When the runtime calls a function, it provides the corresponding object as an argument.

Functions act on objects. They do not belong to them.

TypeScript reference

FLX provides TypeScript definitions to support editor autocompletion and validation.

reference
/// <reference path="https://flxforge.github.io/FLXEngine/scripts/flx.d.ts" />

This enables development assistance in compatible editors such as Visual Studio Code.

flx.d.ts helps the editor understand FLX's public contract; it does not participate in game execution.

Input

Scripts work with logical controls, not physical keys or buttons. Input Mapping connects those controls to physical inputs. If the project does not select a mapping through input.mapping, FLX uses the default mapping.

Input
const MOVE = direction(0);
const FIRE = button(0);

move_horizontal(player, input_direction(player, MOVE, HORIZONTAL));

if (input_pressed(player, FIRE)) {
    spawn(player, "laser");
}

When using a RuntimeObject as an input subject, the object must declare control.player.

Lifecycle

Objects go through different stages during their existence within the runtime.

Lifecycle
Object enters the world
        │
        ▼
      born()
        │
        ▼
 ┌─────────────────┐
 │     action()    │
 │     motion()    │
 │   collision()   │
 │      draw()     │
 └─────────────────┘
        │
        │ kill()
        ▼
      dead()
        │
        ▼
     removed

This terminology is part of FLX's mental model.

Objects are born, exist for a time and eventually disappear.

kill() is not a phase of the execution cycle. It can be requested during the object's life, and from that moment the object stops participating in subsequent active phases. draw() runs during drawing and only for objects that are alive and visible.

Main functions

  • born(object): runs once when an instance enters the world.
  • action(object): main logic and interaction.
  • motion(object): movement and transformations.
  • collision(object, other, contacts): runs when one of the object's enabled colliders includes the other object's group in its with list.
  • dead(object): last opportunity to act before physical removal.

Collision execution rule

A collider without with is passive.

It can be detected by other objects, but does not initiate callbacks.

  • enabled: controls whether a named collider exists.
  • with: defines which groups that collider actively queries.
  • collision(): defines what happens when it finds a match.

Only objects with at least one enabled, compatible collider execute collision(object, other, contacts).

Groups included in with do not automatically execute their own collision handler: each collider's direction is evaluated independently.

Destruction

The alive state of a RuntimeObject is readonly. An instance's death is requested through kill(object).

destroy
kill(laser);

Destruction does not happen immediately.

The runtime marks the object as dead, excludes it from subsequent active phases and schedules its safe removal.

Death flow
kill()
  -> death requested
  -> dead()
  -> cleanup()

This avoids problems during collisions, movement or script execution. dead(object) is terminal: it runs once and cannot resurrect the object.

The object received by dead(object) is a deliberate final context for that hook. It can be used for meaningful final operations, such as spawn(), read_local(), play_sound(), find_parent() and find_children(). Lookup results still come only from the living world.

Use hide(object) and show(object) to control visibility without changing the lifecycle. Hidden objects still update action, motion, collision, timers and state time, but skip both declarative drawing and the JavaScript callback draw(object).

Scopes

Understanding scopes is one of the keys to understanding FLX.

Function scope

Variables declared inside a function exist only during that call.

Function scope
function motion(ship) {
    let thinking = false;
}

Script scope

Variables declared outside functions belong to the script.

Because the script is shared, every object using it shares that state.

Script scope
let laserCounter = 0;

function born(laser) {
    laserCounter++;
}

Object scope

Each object has its own space for storing data through explicit functions:

Object scope
function born(laser) {
    write_local(laser, "lifetime", 0);
}

Data stored with write_local() belongs exclusively to that object.

Object scope
function motion(laser) {
    const lifetime = (read_local(laser, "lifetime") || 0) + delta();
    write_local(laser, "lifetime", lifetime);

    if (lifetime > 2) {
        kill(laser);
    }
}

This distinction is fundamental:

  • Temporary state belongs to the function.
  • State shared by objects using the same script belongs to the script.
  • Individual state belongs to the object.
  • State shared by the entire runtime is managed with read_global() and write_global().

Runtime scope

FLX provides state shared by the entire runtime through read_global() and write_global().

Values stored with write_global() are available to all scripts during runtime execution.

Runtime scope
function born(game) {
    write_global("score", 0);
    write_global("lives", 3);
}

function collision(player, asteroid) {
    write_global("lives", read_global("lives") - 1);
}

This scope is useful for data shared by the entire game, such as score, lives, level state or general counters.

Unlike read_local(), which belongs to a specific instance, read_global() and write_global() access the runtime's shared state.

Program scripts

Program scripts are not part of the current runtime contract.

For now, global game state must be initialized from the born(object) function of the root object.

A dedicated program cycle with explicit phases will be evaluated later: start and end.

Good practices

  • Use JSON to define data.
  • Use scripts to define behavior.
  • Use read_local() and write_local() for individual state.
  • Use script variables only for shared state.
  • Use delta() for timers and time-dependent movement.
  • Use kill() to destroy objects.
  • Use read_global() and write_global() for shared runtime state.
