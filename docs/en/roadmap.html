FLX Documentation

Roadmap

FLX is developed incrementally and through practical experimentation.

Each example adds new runtime capabilities, helps validate real architecture and reveals necessary improvements before moving forward.

This section acts as both a development diary and a general direction overview for the project.

Completed

Pong Example

First functional example used to build and validate the base engine structure.

Implemented systems

  • Base engine structure
  • Initial lifecycle
  • Movement API
  • Basic collisions
  • Horizontal and vertical bounce
  • Basic AI enemy
  • Respawn system (to_origin())
  • Log console
  • JSON and JavaScript support
  • JSON Schemas
  • TypeScript definitions (.d.ts)

In Development

Asteroids Example

Second runtime example.

Currently used to validate:

  • shape system.
  • JSON-based motion system.
  • Rotation and unified FLX angular convention, also applied to Pong.
  • New API functions and runtime scripting evolution.
  • Screen wrapping and bounds behavior system.
  • Living HTML documentation synchronized with real development.
  • Real color support directly from JSON.
  • New shape.type = line support.
  • Scalable input system: Key.down(KEY_*) and Key.pressed(KEY_*).
  • KEY_* constants exposed to JavaScript.
  • Probability system: probability(chance, base).
  • Declarative spawns defined directly in JSON.
  • Prefabs loaded and cached without immediate instantiation.
  • Runtime instantiation through spawn(self, "laser").
  • Dynamic object creation from prefabs.
  • Rotated local offsets based on object angle.
  • Prefab script loading and caching through ScriptEngine.
  • Functional ship shooting system.

Currently in development

  • Object spawning (lasers / asteroids)
  • UI and text
  • More robust lifecycle
  • game / level context
  • Signals and object communication

Planned

Arkanoid Example

  • Basic sound system

Next Phase

After completing the three main examples, FLX will enter a normalization and refinement phase.

The objective will be:

  • Unify architecture and naming
  • Refine APIs
  • Reduce duplication
  • Improve runtime consistency
  • Make the examples more complete and polished

Technical debt and pending improvements

  • Normalize Pong to the new shape/motion schema.
  • Review whether program should remain the final name.
  • Centralize JavaScript wrapper functions to avoid modifying multiple locations for each new lifecycle.
  • Refactor the JS wrapper using a centralized function registry system.
  • Normalize JSON paths the same way scripts are handled.
  • Improve warnings: optional missing lifecycle functions should not generate warnings.
  • Missing optional lifecycle functions should remain silent.
  • Define a more robust lifecycle: gameStart, start, action, motion, collision, draw, end/dead.
  • Define runtime destruction: kill(), dead/end lifecycle.
  • Properly define lifetime, timers and delta management.
  • Define a complete spawn / prefabs / templates system.
  • Implement a safe spawn queue: avoid direct push_back during object iteration.
  • Properly implement motion.inherit = live.
  • Define game/level context and persistent state between levels.
  • Explore a semantic input layer (Control.*) above Key.
  • Properly separate and document block, rectangle and triangle.
  • Improve overflow-aware collisions.
  • Future: wrap-aware collisions using radius and offsets.
