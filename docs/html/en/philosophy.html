FLX Documentation

Philosophy

FLX was born from a simple idea: getting results without fighting the tools.

Too often, simple ideas become buried beneath complex configuration, difficult architectures or workflows that require learning the tool before building the project.

FLX aims to reduce that friction.

Why FLX Exists

FLX is designed for developers who want to build something quickly, understand how it works and keep control over what they are creating.

Whether it is a prototype, a game jam, a complete game or an interactive tool, the goal remains the same:

Build without fighting the engine.

Simplicity Through Understanding

FLX does not try to hide how it works internally.

It does not try to replace C++, nor abstract every runtime detail away.

The idea is different:

use simple and predictable structures so behavior can be understood, modified and extended easily.

Simplicity does not come from hiding complexity.

It comes from organizing it clearly.

Data, Functions and Runtime

FLX is built around three fundamental concepts:

Mental model
Objects -> Data

Scripts -> Functions

Runtime -> Connects both

Objects describe what exists.

Scripts describe what happens.

The runtime coordinates the interaction between both.

This model allows complex behavior to emerge from relatively simple structures.

Built Around Standards

FLX avoids unnecessary proprietary systems.

Projects rely on widely known technologies:

  • JSON for structured data
  • JavaScript for scripting
  • Standard asset formats
  • Readable and editable text files

The goal is to let developers use tools they already know.

High-Level and Low-Level Access

FLX provides high-level helpers to solve common behaviors quickly.

At the same time, it allows developers to work directly with the underlying data when more specific behavior is required.

There are recommended conventions, but no closed paths.

Small, Clear and Direct

FLX is especially suited for:

  • Prototypes
  • Game jams
  • Arcade games
  • Small and medium-sized 2D projects
  • Experimental ideas

It does not try to solve every problem.

It tries to be a clear tool for solving some of them well.

What FLX Is Not Trying To Be

FLX is not trying to compete with large-scale general-purpose engines.

It is not trying to hide runtime behavior behind increasingly complex abstraction layers.

And it is not trying to replace technical understanding with automation.

FLX aims to help developers understand what happens, why it happens and how to change it.

Philosophy explains why FLX exists. The Mental Model explains how it thinks.
