Scripting

Los scripts definen el comportamiento de los objetos durante la ejecución.

Sin embargo, para comprender correctamente el scripting en FLX, es importante olvidar algunas ideas comunes presentes en otros motores.

La idea detrás del scripting en FLX

Muchos motores organizan el comportamiento mediante clases, componentes o sistemas donde cada objeto posee sus propios métodos.

FLX utiliza una aproximación diferente.

Mental model
Objeto  -> Datos

Script  -> Funciones

Runtime -> Conecta ambos

Los objetos contienen estado.

Los scripts contienen funciones.

El runtime ejecuta funciones y les proporciona los objetos sobre los que deben actuar.

FLX no intenta convertir JavaScript en C++.

Intenta que el comportamiento del runtime pueda escribirse como script.

Modelo de scripting

Un script FLX no es una clase.

Tampoco es una instancia independiente para cada objeto.

Es un módulo JavaScript compartido.

El runtime carga el script una sola vez y reutiliza sus funciones para todos los objetos que lo necesiten.

ship.js
function action(ship) {
    accelerate(ship);
}

Cuando el runtime llama una función, proporciona el objeto correspondiente como argumento.

Las funciones actúan sobre los objetos. No pertenecen a ellos.

Referencia TypeScript

FLX proporciona definiciones TypeScript para facilitar autocompletado y validación en el editor.

reference
/// <reference path="https://flxforge.github.io/FLXEngine/scripts/flx.d.ts" />

Esto permite utilizar ayudas de desarrollo en editores compatibles como Visual Studio Code.

Input

Los scripts leen input mediante controles logicos. Las teclas fisicas y botones de mando se declaran en el archivo input.mapping del proyecto, no directamente en scripts.

Input
const MOVE = direction(0);
const FIRE = button(0);

move_horizontal(player, input_direction(player, MOVE, HORIZONTAL));

if (input_pressed(player, FIRE)) {
    spawn(player, "laser");
}

Ciclo de vida

Los objetos atraviesan distintas etapas durante su existencia dentro del runtime.

Lifecycle
Runtime Start
      |
 Object Born
      |
   born()

 action()
 motion()
 collision()

 kill()

 dead()

 cleanup()

Esta terminología forma parte del modelo mental de FLX.

Los objetos nacen, existen durante un tiempo y finalmente desaparecen.

Funciones principales

  • born(object): se ejecuta cuando un objeto entra en el mundo.
  • action(object): lógica principal e interacción.
  • motion(object): movimiento y transformaciones.
  • collision(object, other): se ejecuta cuando el objeto tiene collision.active = true y el grupo del otro objeto está incluido en collision.with.
  • dead(object): última oportunidad de actuar antes de la eliminación física.

Regla de ejecución de colisiones

collision.active no significa que un objeto pueda recibir colisiones.

Significa que ese objeto comprueba colisiones activamente.

  • active: pregunta si hay colisiones.
  • with: define a qué grupos pregunta.
  • collision(): define qué ocurre cuando encuentra una coincidencia.

Solo los objetos activos ejecutan collision(object, other).

Los objetos incluidos en collision.with no ejecutan automáticamente su propio manejador de colisión, salvo que también estén activos y detecten de forma independiente una colisión coincidente.

Destrucción

La destrucción de un objeto se solicita mediante kill(object). Las escrituras directas sobre object.alive son ignoradas por el runtime.

destroy
kill(laser);

La destrucción no ocurre inmediatamente.

El runtime marca el objeto como muerto, lo excluye de las fases activas posteriores y programa su eliminación segura.

Death flow
kill()
  -> death requested
  -> dead()
  -> cleanup()

Esto evita problemas durante colisiones, movimiento o ejecución de scripts. dead(object) es terminal: se ejecuta una vez y no puede resucitar el objeto.

Usa hide(object) y show(object) para controlar la visibilidad sin cambiar el ciclo de vida. Los objetos ocultos siguen actualizando action, motion, collision, timers y state time, pero omiten tanto el dibujado declarativo como el callback JavaScript draw(object).

Ámbitos

Comprender los ámbitos es una de las claves para comprender FLX.

Ámbito de función

Las variables declaradas dentro de una función existen únicamente durante esa llamada.

Function scope
function motion(ship) {
    let thinking = false;
}

Ámbito de script

Las variables declaradas fuera de las funciones pertenecen al script.

Como el script es compartido, todos los objetos que lo utilicen compartirán ese estado.

Script scope
let laserCounter = 0;

function born(laser) {
    laserCounter++;
}

Ámbito de objeto

Cada objeto dispone de un espacio propio para almacenar datos:

Object scope
function born(laser) {
    laser.local["lifetime"] = 0;
}

Los datos almacenados en object.local pertenecen exclusivamente a ese objeto.

Object scope
function motion(laser) {
    laser.local["lifetime"] += delta();

    if (laser.local["lifetime"] > 2) {
        kill(laser);
    }
}

Esta diferencia es fundamental:

  • El estado temporal pertenece a la función.
  • El estado compartido entre objetos del mismo script pertenece al script.
  • El estado individual pertenece al objeto.
  • El estado compartido por todo el runtime pertenece a global.

Ámbito global

FLX proporciona un ámbito global compartido mediante global.

Los valores almacenados en global están disponibles para todos los scripts durante la ejecución del runtime.

Global scope
function born(game) {
    global["score"] = 0;
    global["lives"] = 3;
}

function collision(player, asteroid) {
    global["lives"] -= 1;
}

Este ámbito resulta útil para datos compartidos por todo el juego, como puntuación, vidas, estado de nivel o contadores generales.

A diferencia de object.local, que pertenece a una instancia concreta, global pertenece al runtime.

Scripts de programa

Los scripts de programa no forman parte del contrato actual del runtime.

De momento, el estado global del juego debe inicializarse desde la función born(object) del objeto root.

Más adelante se evaluará un ciclo de programa dedicado con fases explícitas start y end.

Buenas prácticas

  • Utiliza JSON para definir datos.
  • Utiliza scripts para definir comportamiento.
  • Utiliza object.local para estado individual.
  • Utiliza variables de script únicamente para estado compartido.
  • Utiliza delta() para temporizadores y movimiento dependiente del tiempo.
  • Utiliza kill() para destruir objetos de forma segura.
  • Utiliza global para estado compartido del runtime.
