Scripting

Scripts define object behavior during runtime execution.

However, to properly understand scripting in FLX, it is important to leave behind some assumptions commonly found in other engines.

The Idea Behind FLX Scripting

Many engines organize behavior through classes, components or systems where each object owns its own methods.

FLX uses a different approach.

Mental model
Object  -> Data

Script  -> Functions

Runtime -> Connects both

Objects contain state.

Scripts contain functions.

The runtime executes functions and provides the objects they should operate on.

FLX does not try to turn JavaScript into C++.

It tries to make runtime behavior scriptable.

Scripting Model

An FLX script is not a class.

It is not an independent instance per object either.

It is a shared JavaScript module.

The runtime loads the script once and reuses its functions for every object that needs them.

ship.js
function action(ship) {
    accelerate(ship);
}

When the runtime invokes a function, it provides the corresponding object as an argument.

Functions operate on objects. They do not belong to them.

TypeScript Reference

FLX provides TypeScript definitions for autocomplete and editor validation.

reference
/// <reference path="https://flxforge.github.io/FLXEngine/scripts/flx.d.ts" />

This enables development assistance in editors such as Visual Studio Code.

Lifecycle

Objects move through several stages during their existence inside the runtime.

Lifecycle
Runtime Start
      ↓
   start()

 Object Born
      ↓
   born()

 action()
 motion()
 collision()

 kill()

 dead()

 cleanup()

This terminology is part of the FLX mental model.

Objects are born, exist for a period of time, and eventually disappear.

Main Functions

  • start(): executed once when the runtime starts.
  • born(object): executed when an object enters the world.
  • action(object): main logic and interaction.
  • motion(object): movement and transformations.
  • collision(object, other): interaction between objects.
  • dead(object): last opportunity to react before physical removal.

Destruction

Object destruction is requested through kill(object).

destroy
kill(laser);

Destruction does not happen immediately.

The runtime marks the object as dead, excludes it from later phases and schedules safe removal.

Death flow
kill()
   ↓
alive = false
   ↓
dead()
   ↓
cleanup()

This prevents issues during collisions, movement or script execution.

Scopes

Understanding scopes is one of the keys to understanding FLX.

Function Scope

Variables declared inside a function only exist during that invocation.

Function scope
function motion(ship) {
    let thinking = false;
}

Script Scope

Variables declared outside functions belong to the script.

Since scripts are shared, all objects using that script share the same state.

Script scope
let laserCounter = 0;

function born(laser) {
    laserCounter++;
}

Object Scope

Every object provides its own storage area:

Object scope
function born(laser) {
    laser.local["lifetime"] = 0;
}

Data stored inside object.local belongs exclusively to that object.

Object scope
function motion(laser) {
    laser.local["lifetime"] += delta();

    if (laser.local["lifetime"] > 2) {
        kill(laser);
    }
}

This distinction is fundamental:

  • Temporary state belongs to the function.
  • State shared by objects using the same script belongs to the script.
  • Individual state belongs to the object.
  • State shared by the whole runtime belongs to global.

Global Scope

FLX provides a shared global scope through global.

Values stored in global are available to all scripts during runtime execution.

Global scope
function start() {
    global["score"] = 0;
    global["lives"] = 3;
}

function collision(player, asteroid) {
    global["lives"] -= 1;
}

This scope is useful for data shared by the whole game, such as score, lives, level state or general counters.

Unlike object.local, which belongs to a specific instance, global belongs to the runtime.

Program Scripts

Program Scripts execute logic associated with the runtime as a whole.

While object scripts react to the lifecycle of a specific object, Program Scripts react to the lifecycle of the runtime itself.

game.json
"program": {
    "scripts": [
        "scripts/program"
    ]
}

The final shape of these contexts is still evolving.

Best Practices

  • Use JSON to define data.
  • Use scripts to define behavior.
  • Use object.local for per-object state.
  • Use script variables only for shared state.
  • Use delta() for timers and time-based movement.
  • Use kill() for safe object destruction.
  • Use global for shared runtime state.
