FLX Documentation

Roadmap

FLX se desarrolla de forma incremental y práctica.

Cada ejemplo añade nuevas capacidades al runtime, ayuda a validar arquitectura real y permite detectar mejoras necesarias antes de avanzar.

Esta sección funciona como diario de desarrollo y hoja de dirección general del proyecto.

Principio actual de desarrollo

Durante las primeras fases del proyecto, los ejemplos se utilizaban para definir nuevas capacidades del runtime.

El enfoque actual es diferente.

Antes de añadir nuevas funcionalidades, se intenta construir cada ejemplo utilizando únicamente las capacidades ya existentes.

Cuando una limitación impide continuar de forma razonable, esa limitación se convierte en candidata a evolución del runtime.

Este enfoque permite que las nuevas funcionalidades nazcan de necesidades reales detectadas durante el desarrollo, en lugar de aparecer como características diseñadas de forma aislada.

Ejemplo Asteroids

Segundo ejemplo del runtime.

Asteroids representa la primera fase donde FLX empieza a definir su modelo interno.

Más allá del movimiento y los disparos, este ejemplo está ayudando a establecer cómo nacen, viven, interactúan y desaparecen los objetos dentro del runtime.

Pong validó el runtime base. Asteroids está validando el lenguaje con el que se construyen los mundos.

Actualmente utilizado para validar:

  • Sistema de formas (shape).
  • Sistema motion basado en JSON.
  • Rotación y convención angular FLX unificada también en Pong.
  • Nuevas funciones de API y evolución del runtime scripting.
  • Sistema de wrap screen y comportamiento bounds.
  • Documentación HTML viva y sincronizada con el desarrollo real.
  • Soporte de color real desde JSON.
  • Nuevo tipo shape.type = line.
  • Sistema de input escalable: Input.player(index) y Input.system.
  • API normalizada Input expuesta a JavaScript.
  • Sistema probabilístico: probability(chance, base).
  • Hijos manuales declarados directamente en JSON.
  • Definiciones reutilizables cargadas sin instanciación inmediata.
  • Instanciación runtime mediante spawn(object, "laser").
  • Creación dinámica de objetos desde hijos manuales.
  • Spawn queue segura mediante pendingObjects y flushSpawnQueue().
  • Entrada al mundo desacoplada: spawn(), cola, born() y runtime.
  • Offsets locales rotados según el ángulo del objeto.
  • Carga y caché de scripts mediante ScriptEngine.
  • Sistema de disparo funcional desde la nave.
  • Lifecycle completo: born(), action(), motion(), collision(), kill(), dead() y cleanup().
  • Destrucción diferida mediante kill(object).
  • Estado alive para excluir objetos muertos de nuevas fases runtime.
  • Fase dead() ejecutada una sola vez antes del cleanup.
  • Inicialización por instancia mediante born().
  • Estado local persistente por objeto mediante object.local.
  • Tiempo real de frame mediante delta().
  • Modelo de ámbitos: función, script, object.local y futuro ámbito global.
  • Composición de JSON mediante like con sobrescritura recursiva de propiedades.
  • Reutilización de configuraciones mediante definiciones reutilizables y derivadas.
  • Resolución de rutas relativas desde el JSON que las declara.
  • Children inline definidos directamente dentro de estructuras JSON.
  • Nodos lógicos sin representación visual.
  • Nuevo tipo shape.type = polygon.
  • Formas poligonales definidas mediante listas de puntos.
  • Generación aleatoria mediante random(min, max).
  • Spawners reutilizables construidos mediante like.
  • Spawn periódico basado en temporizadores mediante object.local.
  • Limitación local de entidades por spawner.
  • Validación práctica completa del flujo Asteroids: nave, láseres, spawners, asteroides y colisiones básicas.
  • Refinamiento del sistema de asteroides: comportamiento y variantes.
  • Mejoras en el sistema de colisiones.
  • Añadido sistema de visualización de colisiones y tipos de colisiones (circle y box)
  • Refinamiento del sistema de asteroides: fragmentación.
  • Mejoras graficas para mejorar el "juice": estelas, particulas al romperse...
  • UI y texto.
  • Sistema de puntuación y estado global del juego.
  • Contexto game / level.
  • Señales y comunicación entre objetos.

En planificación

Fase posterior

Tras completar los tres ejemplos principales, FLX entrará en una fase de normalización y mejora general.

El objetivo será:

  • Unificar arquitectura y nomenclatura
  • Refinar APIs
  • Reducir duplicidades
  • Mejorar consistencia de runtime
  • Hacer los ejemplos más completos y atractivos

Deuda técnica y mejoras pendientes

Runtime

  • Normalizar Pong al nuevo esquema shape/motion.
  • Extender object.local. Actualmente solo soporta valores numéricos; quedan pendientes tipos como bool, string y posiblemente estructuras más complejas.
  • Definir contextos game/level y persistencia entre niveles.
  • Definir relaciones entre objetos del runtime: parent, children y acceso mediante group.
  • Definir propagación configurable de muerte, permitiendo decidir si kill(parent) debe afectar también a sus hijos.
  • Implementar correctamente motion.inherit = live.
  • Definir una identidad única de runtime (runtimeId) para cada instancia.
  • Validar argumentos obligatorios de la API JavaScript y registrar advertencias cuando sean inválidos.

Lifecycle y contextos de script

  • Evaluar un ciclo dedicado para scripts de programa a nivel de juego.
  • Evaluar y formalizar: start(), update(), end() y draw().
  • Definir si los scripts de programa se declaran en el manifiesto .flx o mediante un futuro contrato runtime del root.

Motor y arquitectura

  • Centralizar los wrappers JavaScript para evitar modificar múltiples ubicaciones cuando se añadan nuevas fases del lifecycle.
  • Refactorizar los wrappers JS mediante un registro centralizado de funciones.
  • Centralizar completamente la normalización de rutas para evitar lógica duplicada entre recursos, definiciones de objeto y scripts.
  • Mejorar las advertencias: las funciones opcionales del lifecycle no deberían generar avisos cuando no existan.
  • Explorar una capa semántica de entrada (Control.*) sobre Key.
  • Evaluar nuevas opciones de runtime debug.*: debug.bounds, debug.origins, debug.lifecycle, debug.scripts, debug.fps y debug.metrics.

Ayudas graficas y audio

  • Ampliar fade_on() y fade_off() con parametros opcionales de duracion e intensidad.
  • Explorar datos de audio declarativo mas ricos manteniendo play_sound(object, id) simple.

Espacios de coordenadas y sistema de cámara

  • Definir y documentar los espacios de coordenadas: mundo, pantalla, local y cámara/vista.
  • Definir cómo afectan estos espacios a: origin, offset, posiciones de spawn, draw_text(), límites, colisiones, transformaciones padre/hijo y renderizado de interfaz.
  • Diseñar e implementar sistemas de cámara y scroll.

Datos y composición JSON

  • Implementar correctamente shape.like y definir su comportamiento dentro del sistema de composición.
  • Reflejar correctamente el sistema like en los esquemas JSON y en la documentación.
  • Documentar formalmente la composición JSON mediante like, incluyendo reglas de merge y sobrescritura.
  • Implementar un sistema de constantes.
  • Ejemplo: constants["INIT_LIVES"]

Colisiones y física

  • Mejorar las colisiones con soporte de overflow.
  • Futuro: colisiones conscientes de wrap utilizando radios y offsets.
  • Permitir múltiples colliders por elemento.
  • Añadir filtros de colisión: grupos, máscaras, prioridades y reglas relacionadas.
  • Actualmente la colisión de cajas está alineada con los ejes y no rota. La colisión circular es independiente de la rotación.

Audio

  • Diseñar e implementar el sistema de audio.

Transformaciones y jerarquías

  • Permitir que los objetos hijos sigan las transformaciones de sus padres.

Herramientas futuras

  • Evaluar la incorporación futura de spawnRandom() como helper de alto nivel.
  • Explorar una herramienta visual para crear y editar formas poligonales.
  • Explorar una herramienta visual para composición JSON y definiciones reutilizables.

Helpers futuros de API

  • lerp(start, end, factor)
  • scale()
  • bounce(object, other)
  • Helpers matemáticos: sin(angle), cos(angle), atan2(y, x), distance(a, b), angle_to(a, b).
