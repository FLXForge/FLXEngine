Input Chip define qué controles lógicos existen. Declara sus presupuestos y sus reglas de resolución. La entrada física que activa cada control se asigna en otro archivo, el Input Mapping.

Controles y defaults

Presupuestos independientes
CampoTipo / valoresDefaultComportamiento en v0.3.0
system.buttonsEntero ≥ 02Botones lógicos globales, independientes de jugador. El chip no les asigna semánticas como Start o Select.
players.countEntero ≥ 11Número de jugadores lógicos disponibles.
players.controls.buttonsEntero ≥ 04Número de botones lógicos por jugador.
players.controls.directionsArray no vacío de mapasUna dirección 4wayLista de controles direccionales independientes disponibles para cada jugador. Un array declarado reemplaza la lista por defecto.

Los jugadores se identifican desde 1; los botones y las direcciones desde 0. Por ejemplo, dos direcciones por jugador son direction 0 y direction 1. Omitir directions conserva la dirección por defecto; declararlo vacío produce diagnóstico de error.

Default Input Chip
machine:
  input:
    system:
      buttons: 2
    players:
      count: 1
      controls:
        buttons: 4
        directions:
          - type: 4way
            simultaneous: last
            buffer: 0

4way

Convención de signos por eje
        UP (−1)
           │
LEFT (−1) ─┼─ RIGHT (+1)
           │
       DOWN (+1)

Un control 4way tiene una única componente lógica activa, o neutral. No genera diagonales: simultaneous decide qué componente prevalece. La convención de consulta por eje es UP = −1 y DOWN = +1 en vertical; LEFT = −1 y RIGHT = +1 en horizontal. Son signos del estado direccional, no una declaración de constantes JavaScript adicionales.

2way

Estado lógico
NEGATIVE (−1) ← neutral (0) → POSITIVE (+1)

El mapping público puede utilizar los nombres up, right, down y left. Para un control 2way se normalizan como sigue:

Normalización de nombres del mapping
Nombre públicoComponente lógica
up, leftnegative (−1)
down, rightpositive (+1)

Esta agrupación identifica alternativas para una misma componente; no exige activar ambos nombres a la vez. La política simultaneous opera sobre las componentes normalizadas.

Simultaneous

Resolución de simultaneidad
ValorComportamiento
lastGana la última componente activada entre las que siguen activas.
firstLa componente dominante conserva el control mientras siga activa. Al desaparecer, puede promoverse una candidata pendiente válida; si no la hay, se resuelve de nuevo entre las componentes que continúan activas.
neutralMás de una componente activa produce neutral; una única componente activa se conserva.

Cada dirección resuelve su propia simultaneidad. Tener varias direcciones por jugador no las convierte en un único control combinado.

Buffer

Buffer no es una cola genérica de input. En simultaneous: first, permite conservar temporalmente una componente candidata bloqueada mientras otra mantiene la dominancia. Esa candidata puede tomar el control cuando desaparece la dominante, siempre que siga activa. El tiempo se expresa en segundos.

No garantiza ejecutar después una pulsación ya liberada: una candidata que deja de estar activa se descarta. Con last o neutral, buffer no modifica la resolución. El default 0 no conserva una candidata mediante este mecanismo.

Dos controles direccionales por jugador
machine:
  input:
    players:
      count: 1
      controls:
        buttons: 2
        directions:
          - type: 4way
            simultaneous: first
            buffer: 0.15
          - type: 2way
            simultaneous: neutral
            buffer: 0

Fragmento válido de mapping

Estas entradas físicas pertenecen al mapping, no a la definición de Machine Input. El proyecto selecciona el archivo mediante input.mapping en Project. Cambiar las asociaciones físicas no debería requerir cambiar el mundo JSON ni los scripts que consultan los mismos controles lógicos.

Las llamadas de lectura se documentan en FLX API. La asociación de un objeto con un jugador pertenece a Object.control.

Capacidades no soportadas

input.pointer e input.text no son capacidades disponibles en v0.3.0. Declararlas produce un diagnóstico de Machine no soportada. Del mismo modo, no se aceptan como implementados tipos direccionales distintos de 2way y 4way. No son campos futuros silenciosamente operativos.
