FLX Documentation

Roadmap

FLX is developed incrementally and practically.

Each example adds new runtime capabilities, helps validate real architecture and reveals necessary improvements before moving forward.

This section works as both a development journal and a general direction map for the project.

Current Development Principle

During the earliest stages of the project, examples were used to define new runtime capabilities.

The current approach is different.

Before adding new functionality, each example is built using only the capabilities already available.

When a limitation prevents reasonable progress, that limitation becomes a candidate for runtime evolution.

This approach allows new features to emerge from real needs discovered during development, instead of appearing as isolated design decisions.

Asteroids Example

Second runtime example.

Asteroids represents the first phase where FLX begins to define its internal model.

Beyond movement and shooting, this example helped establish how objects are born, live, interact and disappear within the runtime.

Pong validated the core runtime. Asteroids validated the language used to build worlds.

Systems validated through Asteroids:

  • Shape system (shape).
  • JSON-driven motion system.
  • Rotation and the unified FLX angular convention, also applied to Pong.
  • New API functions and runtime scripting evolution.
  • Screen wrapping and bounds behavior.
  • Living HTML documentation synchronized with real development.
  • Real color support from JSON.
  • New shape.type = line shape.
  • Scalable input system: button(index), direction(index), player(index) and system().
  • Logical input query API exposed to JavaScript.
  • Probability system: probability(chance, base).
  • Manual children declared directly in JSON.
  • Reusable object definitions loaded without immediate instantiation.
  • Runtime instantiation through spawn(object, "laser").
  • Dynamic object creation from manual children.
  • Safe spawn queue through pendingObjects and flushSpawnQueue().
  • Decoupled world entry: spawn(), queue, born() and runtime integration.
  • Local offsets rotated according to object angle.
  • Script loading and caching through ScriptEngine.
  • Functional ship firing system.
  • Complete lifecycle: born(), action(), motion(), collision(), kill(), dead() and cleanup().
  • Deferred destruction through kill(object).
  • State flag alive used to exclude dead objects from subsequent runtime phases.
  • dead() phase executed exactly once before cleanup.
  • Per-instance initialization through born().
  • Persistent per-object state through object.local.
  • Real frame timing through delta().
  • Scope model: function scope, script scope, object.local and future global scope.
  • JSON composition through like with recursive property overriding.
  • Configuration reuse through reusable and derived definitions.
  • Relative path resolution from the JSON file that declares the reference.
  • Inline children defined directly inside JSON structures.
  • Logical nodes without visual representation.
  • New shape.type = polygon shape.
  • Polygonal shapes defined through point lists.
  • Random generation through random(min, max).
  • Reusable spawners built through like.
  • Periodic spawning driven by timers through object.local.
  • Local entity limits per spawner.
  • Full practical validation of the Asteroids gameplay loop: ship, lasers, spawners, asteroids and basic collisions.
  • Asteroid system refinement: behaviors and variants.
  • Collision system improvements.
  • Collision visualization and support for circle and box colliders.
  • Asteroid system refinement: fragmentation.
  • Visual improvements to increase game feel: trails, destruction particles and related effects.
  • UI and text systems.
  • Score system and global game state.
  • game / level context.
  • Signals and object-to-object communication.

Later Phase

After completing the three main examples, FLX will enter a normalization and general improvement phase.

The goal will be:

  • Unify architecture and naming
  • Refine APIs
  • Reduce duplication
  • Improve runtime consistency
  • Make examples more complete and attractive

Technical Debt and Pending Improvements

Runtime

  • Normalize Pong to the new shape/motion schema.
  • Extend object.local. It currently supports only numeric values; types such as bool, string and possibly more complex structures remain pending.
  • Define game/level contexts and persistence between levels.
  • Define runtime object relationships: parent, children and access through group.
  • Define configurable death propagation, allowing decisions such as whether kill(parent) should also affect its children.
  • Properly implement inherit.live.
  • Define a unique runtime identity (runtimeId) for each instance.
  • Validate required JavaScript API arguments and log warnings when invalid.

Lifecycle and Script Contexts

  • Evaluate a dedicated program script lifecycle for game-level scripts.
  • Evaluate and formalize: start(), update(), end() and draw().
  • Define whether program scripts are declared in the .flx manifest or through a future root-level runtime contract.

Engine and Architecture

  • Centralize JavaScript wrapper functions to avoid modifying multiple locations whenever a new lifecycle is introduced.
  • Refactor the JS wrapper using a centralized function registry.
  • Fully centralize path normalization and keep JSON/script resolution outside Engine.
  • Improve warnings: optional lifecycle functions should not generate warnings when absent.
  • Explore a semantic input layer (Control.*) on top of Key.
  • Evaluate additional runtime debug.* options: debug.bounds, debug.origins, debug.lifecycle, debug.scripts, debug.fps and debug.metrics.

Graphics and Audio Helpers

  • Extend fade_on() and fade_off() with optional duration and intensity parameters.
  • Explore richer declarative audio data while keeping play_sound(object, id) simple.

Coordinate Spaces and Camera System

  • Define and document coordinate spaces: world, screen, local and camera/view coordinates.
  • Define how coordinate spaces affect: origin, offset, spawn positions, draw_text(), bounds, collisions, parent/child transforms and UI rendering.
  • Design and implement camera and scrolling systems.

Data and JSON Composition

  • Properly implement shape.like and define its behavior within the composition system.
  • Correctly reflect the like system in JSON Schemas and documentation.
  • Formally document JSON composition through like, including merge and override rules.
  • Implement a constants system.
  • Example: constants["INIT_LIVES"]

Collisions and Physics

  • Improve overflow-aware collisions.
  • Future: wrap-aware collisions using radii and offsets.
  • Allow multiple colliders per element.
  • Add collision filters: groups, masks, priority and related rules.
  • Box collision is currently axis-aligned and does not rotate. Circle collision is rotation-independent.

Audio

  • Design and implement the audio system.

Transforms and Hierarchies

  • Child objects following parent transforms.

Future Tools

  • Evaluate the future addition of spawnRandom() as a high-level helper.
  • Explore a visual tool for creating and editing polygonal shapes.
  • Explore a visual tool for JSON composition and reusable definitions.

Future API Helpers

  • lerp(start, end, factor)
  • scale()
  • bounce(object, other)
  • Math helpers: sin(angle), cos(angle), atan2(y, x), distance(a, b), angle_to(a, b).
